## 1. 产品概述

工地考勤记账是一款面向小型施工团队、包工头、班组长的微信小程序。产品目标是把原本依赖纸笔、微信群和口头确认的工人管理、月度考勤、借支登记，迁移到微信小程序中完成，形成一套轻量、低学习成本、可公示、可追溯的数字化台账。

V1 是最小可用版本，解决三个核心问题：

1. 管理员能快速建立“工人档案 + 项目档案 + 借支记录”。
2. 员工能通过微信绑定身份，并自行提交上月考勤。
3. 管理员能按月查看谁已填报、谁未填报，并生成基础公示结果。

## 2. 背景与问题

### 2.1 行业背景

建筑劳务/班组管理中，常见流程依赖线下登记：

1. 员工信息散落在通讯录、纸张、微信群。
2. 月度考勤需要人工催收，易漏报、错报。
3. 借支记录常凭口头、转账截图或零钱记录保存，后期对账困难。
4. 员工与管理员对同一笔借支、同一月考勤，缺乏统一查看入口。

### 2.2 当前痛点

| 角色 | 核心痛点 |
| --- | --- |
| 管理员 | 记账散、催收难、月底对账慢、项目与人员状态不同步 |
| 员工 | 不知道自己被记了多少借支，不清楚某月考勤结果，缺少自助查看入口 |
| 团队整体 | 缺少统一台账，月底公示与核对成本高 |

## 3. 产品目标与非目标

### 3.1 目标

1. 将员工建档、项目建档、借支登记、考勤填报全部移动化。
2. 让员工通过微信身份完成自助绑定与自助填报。
3. 形成“月”为单位的考勤记录和借支台账，方便后续核对。
4. 让管理员可直接在首页看到填报进度和未填报名单。

### 3.2 非目标

1. 不做工资核算与工资发放。
2. 不做复杂审批流。
3. 不做多组织、多公司、多层级权限。
4. 不做 ERP 级财务系统集成。

## 4. 用户角色

### 4.1 管理员

- 典型身份：包工头、班组长、现场管理者。
- 核心诉求：能快速建档、记账、催考勤、导出核对结果。

### 4.2 员工

- 典型身份：木工、钢筋工、水电工、泥工等工地工人。
- 核心诉求：绑定自己的微信账号，查看自己的借支和考勤，提交上月考勤。

## 5. 核心业务场景

### 5.1 管理员首次建档

1. 管理员通过邀请码进入系统。
2. 创建工人资料。
3. 创建项目资料。
4. 后续为工人登记借支，等待员工绑定。

### 5.2 员工绑定身份

1. 员工打开小程序。
2. 选择“我是员工”。
3. 从未绑定工人列表中选择本人。
4. 完成微信绑定，后续以该身份查看数据。

### 5.3 员工提交上月考勤

1. 员工进入“填报上月考勤”。
2. 选择月份与参与项目。
3. 填写各项目出勤天数和备注。
4. 提交后当月数据锁定，若需修改联系管理员。

### 5.4 管理员月底汇总

1. 管理员在首页查看当月应填报、已填报、未填报人数。
2. 对未填报人员进行催办。
3. 打开公示报表，按工人查看项目与天数明细。

## 6. 产品范围

### 6.1 本期范围

1. 角色识别与管理员邀请码登录。

5. 员工借支登记与查询。
6. 员工上月考勤填报与历史查看。

## 8. 详细需求

### 8.1 角色与登录

| 编号 | 需求 |
| --- | --- |
| FR-001 | 用户首次进入时必须先进行角色识别。 |
| FR-002 | 管理员需输入有效邀请码方可注册或升级为管理员。 |
| FR-003 | 普通用户不输入邀请码时，不自动创建管理员账号。 |
| FR-004 | 员工首次进入后需完成工人身份绑定。 |

### 8.2 员工管理

| 编号 | 需求 |
| --- | --- |
| FR-101 | 管理员可新增、编辑工人资料。 |
| FR-102 | 工人资料至少包含姓名、手机号、班组、绑定状态。 |
| FR-103 | 管理员可按姓名/手机号搜索员工。 |
| FR-104 | 管理员可筛选已绑定/未绑定员工。 |
| FR-105 | 员工可修改自己的姓名、手机号、班组。 |

### 8.3 项目管理

| 编号 | 需求 |
| --- | --- |
| FR-201 | 管理员可新增项目。 |
| FR-202 | 项目至少包含名称、状态、创建时间。 |
| FR-203 | 管理员可编辑项目名称。 |
| FR-204 | 项目支持“进行中/已完工”状态。 |
| FR-205 | 员工填报考勤时仅能选择可用项目。 |

### 8.4 借支管理

| 编号 | 需求 |
| --- | --- |
| FR-301 | 管理员可为任意员工记录一笔借支。 |
| FR-302 | 借支字段至少包含工人、金额、日期、支付方式、备注。 |
| FR-303 | 管理员可查看、编辑、删除借支记录。 |
| FR-304 | 员工仅能查看自己的借支记录与累计借支金额。 |

### 8.5 考勤填报

| 编号 | 需求 |
| --- | --- |
| FR-401 | 员工只能填报“上个月及更早月份”的考勤。 |
| FR-402 | 单月考勤以员工为维度保存，一条记录内可含多个项目 entries。 |
| FR-403 | 员工可对多个项目分别填写出勤天数与备注。 |
| FR-404 | 单项目出勤天数不得小于 0，且不得大于当月自然日。 |
| FR-405 | 所有项目出勤天数总和不得大于当月自然日。 |
| FR-406 | 同一员工同一月份重复提交时，系统以最新结果覆盖旧记录。 |
| FR-407 | 员工提交后页面应显示已提交状态。 |

### 8.6 月度汇总与公示

| 编号 | 需求 |
| --- | --- |
| FR-501 | 管理员首页展示应填报、已填报、未填报人数。 |
| FR-502 | 首页展示未填报名单。 |
| FR-503 | 管理员可按月切换查看汇总。 |
| FR-504 | 管理员可生成月度考勤公示页，按工人展示项目明细与总天数。 |
| FR-505 | 公示页支持分享给员工核对。 |

## 9. 业务规则

1. 一个微信号只能绑定一个工人账号。
2. 一个工人账号只能被一个微信号绑定一次。
3. 未绑定员工不能查看员工端数据。
4. 管理员可查看全部员工数据，员工仅可查看自己的数据。
5. 月度考勤存储时采用 `attendance + entries[]` 结构，便于同月多项目填报。

## 10. 数据模型

| 集合 | 核心字段 |
| --- | --- |
| `users` | `_openid`、`name`、`phone`、`role`、`createTime` |
| `workers` | `name`、`phone`、`team`、`status`、`openid`、`bindTime` |
| `projects` | `name`、`status`、`createTime`、`finishTime` |
| `attendance` | `worker_id`、`month`、`entries[]`、`submitted_at` |
| `advances` | `worker_id/workerId`、`worker_name/workerName`、`amount`、`date`、`method`、`remark` |

## 11. 权限设计

| 能力 | 管理员 | 员工 |
| --- | --- | --- |
| 查看全部员工 | 是 | 否 |
| 编辑员工资料 | 是 | 仅本人 |
| 新增/编辑项目 | 是 | 否 |
| 新增/编辑借支 | 是 | 否 |
| 查看全部借支 | 是 | 否 |
| 查看本人借支 | 否 | 是 |
| 查看全部考勤明细 | 是 | 否 |
| 提交本人考勤 | 否 | 是 |

## 12. 成功指标

1. 员工绑定率大于 70%。
2. 月度考勤提交率大于 85%。
3. 管理员月底汇总时间由“半天”缩短到“30 分钟内”。
4. 员工关于“我这个月考勤是多少”的重复询问显著减少。

## 13. 非功能需求

1. 页面流程必须适配微信内低学习成本使用，不依赖培训手册。
2. 核心页面加载时间目标小于 2 秒。
3. 关键操作必须有加载态、成功态、失败态反馈。
4. 角色权限必须后端校验，不能仅依赖前端隐藏按钮。

## 14. 发布计划

| 阶段 | 目标 |
| --- | --- |
| 第 1 周 | 完成登录、绑定、员工/项目基础建档 |
| 第 2 周 | 完成借支登记与员工查看 |
| 第 3 周 | 完成员工考勤填报与历史查看 |
| 第 4 周 | 完成管理员月度看板与公示页，试点上线 |

## 15. 风险与依赖

1. 员工数字化能力参差不齐，需要流程足够简单。
2. 微信绑定后不可轻易解绑，误绑定需有人工纠正方案。
3. 项目与借支字段命名需统一，否则后续报表会出现兼容成本。
4. 云数据库权限配置错误会导致页面能看不能写。

## 16. 开放问题

1. 员工是否允许撤回已提交考勤，还是必须经管理员修改。
2. 借支是否需要补充“原因”字段，方便后续工资结算。
3. 员工是否需要看到项目维度的历史考勤趋势。

## 17. 验收标准

1. 管理员能完成工人、项目、借支三类基础建档。
2. 员工能完成微信绑定，并查看自己的资料、借支、考勤。
3. 员工能成功提交上月考勤，且管理员能在看板中看到提交进度变化。
4. 管理员能生成按月公示的考勤列表。
