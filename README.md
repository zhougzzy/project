# 工地考勤记账：我的 AI Coding 产品实践

> 这是我独立完成的一个微信小程序项目。
>
> 我以真实的工地管理场景为起点，使用 AI Coding 完成了从问题分析、需求设计、PRD 拆解、界面设计、代码实现，到功能验收和持续迭代的完整过程。
>
> 项目地址：[github.com/zhougzzy/project](https://github.com/zhougzzy/project)

## 一、项目定位

我将这个项目定位为一个面向小型施工团队的轻量级数字化工具，主要解决员工建档、项目管理、借支登记、月度考勤和员工核对等问题。

项目不是单纯的 CRUD 练习，也不是只展示页面效果的 Demo。我的重点是把一个模糊的业务问题，转化为 AI Coding Agent 能够理解、执行、验证和迭代的开发任务。

这也是我在 AI 产品经理方向上的一次实践：

- 从用户场景中提炼问题，而不是直接开始写代码；
- 用 PRD 明确目标、角色、范围和业务规则；
- 用约束条件降低 AI 生成代码的不确定性；
- 用任务卡把大需求拆成可执行的工作单元；
- 用验收标准判断 Agent 的输出是否真正满足需求；
- 用真实运行结果推动下一轮需求和产品优化。

## 二、我解决了什么问题

### 1. 原始业务问题

小型施工团队通常使用纸张、微信群、聊天记录或个人表格管理人员和账目，容易出现：

- 员工信息分散，绑定关系不清晰；
- 月度考勤依靠人工催收，容易漏报和错报；
- 借支记录缺少统一入口，月底核对成本高；
- 员工不知道自己的考勤和借支是否准确；
- 管理员收到疑问后，需要反复翻找上下文；
- 项目完工后仍出现在可选项目中，影响后续填报。

### 2. 产品目标

我把产品目标分成三个阶段：

| 阶段 | 目标 | 主要能力 |
| --- | --- | --- |
| V1 记录 | 先让业务能够被数字化记录 | 员工、项目、借支、考勤、绑定 |
| V2 提效 | 减少管理员月底整理和催办时间 | 月度看板、筛选、导出、项目状态 |
| V3 协同 | 让记录可核对、问题可处理 | 疑问反馈、管理员处理、分享直达 |

### 3. 非目标

为了控制项目范围，我明确排除了以下内容：

- 工资核算和工资发放；
- ERP、银行或企业微信对接；
- 多公司、多组织、多层级权限；
- 复杂审批流；
- 法务级电子签名和不可篡改审计。

这一步帮助我避免让 AI Agent 在开发过程中不断扩大需求边界。

## 三、需求设计：我如何把业务问题写成可执行需求

我没有直接向 AI Agent 提出“帮我做一个工地管理系统”，而是先拆分用户、场景、规则和验收结果。

### 1. 用户角色

| 角色 | 核心诉求 | 主要操作 |
| --- | --- | --- |
| 管理员 | 建档、记账、催办、导出、处理疑问 | 管理全量数据 |
| 员工 | 绑定身份、填报考勤、查看借支、提出疑问 | 只能操作本人数据 |

### 2. 关键用户流程

#### 员工绑定

1. 员工进入小程序并选择身份。
2. 从未绑定员工中选择本人。
3. 完成微信身份绑定。
4. 后续通过微信身份访问个人数据。

#### 员工考勤填报

1. 员工进入考勤填报页面。
2. 选择允许填报的月份和项目。
3. 填写各项目出勤天数和备注。
4. 提交后形成员工当月考勤记录。
5. 管理员在月度看板中看到进度变化。

#### 借支疑问处理

1. 员工在自己的借支记录中点击“有疑问”。
2. 填写疑问内容并提交。
3. 管理员看到待处理疑问。
4. 管理员查看员工、借支和历史记录。
5. 管理员修改或删除记录，并将疑问标记为已处理。

### 3. 需求必须包含的字段

我为每条需求固定了以下信息：

- **目标**：要解决什么问题；
- **角色**：谁使用；
- **场景**：在什么业务流程中发生；
- **范围**：影响哪些页面、云函数和数据集合；
- **非目标**：本次明确不做什么；
- **业务规则**：数据和权限必须遵守什么规则；
- **技术约束**：必须使用或不能改变什么；
- **验收标准**：如何判断已经完成。

## 四、约束设计：我如何减少 AI Coding 的不确定性

AI 生成代码的效率很高，但如果没有边界，容易出现“能运行但不符合业务”的结果。因此我把约束写进需求和任务卡，而不是只在对话中口头说明。

### 1. 业务约束

- 一个微信 OpenID 只能绑定一个员工；
- 一个员工只能绑定一个微信身份；
- 员工只能查看自己的借支和考勤；
- 管理员权限必须在云函数中校验；
- 已完工项目不能出现在新的考勤填报选择器中；
- 同一员工同一月份重复提交考勤时，使用最新结果覆盖；
- 单项目出勤天数不能小于 0，也不能超过当月自然日；
- 所有项目出勤天数总和不能超过当月自然日。

### 2. 数据兼容约束

项目迭代过程中发现历史借支数据存在字段命名差异：

- `worker_id` / `workerId`
- `worker_name` / `workerName`

因此我要求 Agent 在统一新字段的同时，保留历史数据读取能力，避免为了重构字段而丢失旧记录。

### 3. 技术约束

- 使用微信小程序原生技术栈；
- 使用微信云开发 CloudBase，不额外引入复杂后端服务；
- 云函数使用 `cloud.DYNAMIC_CURRENT_ENV`；
- 每个云函数保持独立目录和依赖；
- 导出能力使用 `node-xlsx`；
- 优先复用已有的 `miniprogram/utils/cloudCall.js`；
- 不在前端隐藏按钮的基础上假设权限安全；
- 不提交 AppSecret、用户隐私数据和生产导出文件。

### 4. 设计约束

我在 `DESIGN.md` 中进一步约束了界面方向：

- 面向低学习成本的移动端操作；
- 白色和浅灰背景为主；
- 蓝色作为主要操作色；
- 状态优先，待处理、已提交、异常需要快速识别；
- 重要操作位于拇指可触达区域；
- 列表信息强调扫描效率，不追求装饰性效果。

## 六、我如何使用 AI Coding 完成开发

### 1. 先让 AI 帮我理解问题，再让 AI 写代码

我的工作顺序不是直接生成页面，而是：

1. 梳理业务背景和用户痛点；
2. 明确角色、流程和权限；
3. 输出 PRD 和数据模型；
4. 分析现有代码和目录结构；
5. 将需求拆成任务卡；
6. 让 Coding Agent 逐张执行；
7. 根据运行结果和验收结果继续迭代。

AI 在这里承担的是“实现协作者”和“分析助手”，产品目标、范围、约束和最终判断仍由我负责。

### 2. 我给 Coding Agent 的上下文

每次开始任务前，我会提供：

- 当前任务卡；
- 对应 PRD 章节；
- 相关页面和云函数路径；
- 数据集合和字段约束；
- 权限边界；
- 设计规范；
- 验收标准；
- 不允许改变的已有行为。

这样做的目的，是让 Agent 在局部上下文中完成可验证的修改，而不是让它自行猜测整个项目。

### 3. Agent 执行流程

我将 Agent 的工作固定为六步：

1. **理解**：复述任务目标、角色和边界；
2. **勘察**：读取相关代码，列出调用链和影响文件；
3. **设计**：给出最小实现方案和数据契约；
4. **实现**：只修改任务范围内的代码；
5. **验证**：执行静态检查和人工验收场景；
6. **交付**：报告修改文件、验收结果、风险和后续任务。

### 4. 我要求 Agent 输出什么

```md
## 实现摘要

## 修改文件

## 数据与权限变更

## 验收结果
- [x] AC-1 ...
- [ ] AC-2 ...（原因）

## 风险与后续
```

这个输出格式让我能够快速判断：Agent 做了什么、改了什么、哪些结果被验证、哪些问题还没有解决。

## 七、结构化任务与任务卡

我使用任务卡替代“想到什么改什么”的开发方式。任务卡遵循以下结构：

```md
# [TASK-XXX] 任务标题

## 目标
说明用户问题和预期结果。

## 角色与场景
说明谁在什么流程中使用。

## 修改范围
页面、云函数、集合、索引和文档。

## 约束
业务规则、权限、安全、兼容和设计要求。

## 验收标准
使用 Given / When / Then 描述可验证结果。

## 交付物
代码、数据变更、验证记录和文档更新。
```

### 任务卡示例：考勤提交

```md
# TASK-008：考勤提交校验与幂等覆盖

## 目标
保证员工提交的月度考勤合法，并避免重复提交产生重复记录。

## 约束
- 只能提交上月及更早月份；
- 单个项目天数不能小于 0；
- 单个项目天数不能大于当月自然日；
- 所有项目天数总和不能超过当月自然日；
- 同一员工同一月份只有一条有效记录。

## 验收标准
- Given 员工选择当前月份，When 提交考勤，Then 系统拒绝并提示月份不可用。
- Given 项目天数超过当月自然日，When 提交，Then 系统拒绝并提示原因。
- Given 员工重复提交同一月份，When 保存成功，Then 旧记录被最新结果覆盖。
- Given 提交成功，When 返回页面，Then 页面显示已提交状态。
```

- `TASK-016`：管理员和员工数据权限校验；

## 九、验收标准：我如何判断功能真正完成

我没有把“页面能打开”作为完成标准，而是从业务结果、权限、安全和异常状态四个层面验收。

### 1. 核心业务验收

- 管理员可以完成员工、项目、借支建档；
- 员工可以完成微信绑定；
- 员工可以查看个人考勤和借支；
- 员工可以提交上月考勤；
- 管理员可以看到月度提交进度；
- 管理员可以生成考勤公示和导出文件；
- 员工可以提交借支疑问；
- 管理员可以处理疑问并关闭状态。

### 2. 权限验收

- 员工不能通过修改参数读取其他员工数据；
- 非管理员不能执行全员数据写操作；
- 非管理员不能执行导出操作；
- 未绑定员工不能进入个人数据链路。

### 3. 异常验收

- 网络失败有提示；
- 云函数业务失败有提示；
- 空数据有空状态；
- 列表加载有加载态；
- 重复点击不会造成重复提交；
- 无效分享参数不会导致白屏。

### 4. 发布验收

- AppID 和云环境配置正确；
- 数据集合和索引已创建；
- 云函数依赖已安装并部署；
- 云存储上传和预览正常；
- 员工、考勤、借支导出文件能够打开；
- 发布包不包含敏感信息和生产临时文件。

## 十、我的产品与工程复盘

### 1. 我对 AI Coding 的理解

在这个项目中，AI Coding 对我来说不是“输入一句话生成完整产品”，而是一种新的产品开发协作方式：

> 我负责定义问题、用户、目标、范围、约束和验收标准；AI Agent 负责在明确上下文中完成分析、实现、检查和迭代。

### 2. 我形成的工作方法

- 先写问题和用户场景，再写功能；
- 先定义验收标准，再让 Agent 实现；
- 先拆任务卡，再进入编码；
- 先读取现有代码，再决定修改方式；
- 先验证业务结果，再判断代码是否完成；
- 保留未完成项和已知限制，不把规划描述成已交付。

### 3. 我观察到的风险

- AI 容易把前端隐藏按钮误认为权限控制，因此权限必须在云函数校验；
- AI 容易忽略旧数据字段，因此数据兼容要写进任务约束；
- AI 容易扩大修改范围，因此每张任务卡都要明确非目标；
- AI 容易只验证主流程，因此验收必须覆盖异常、空状态和越权场景；
- AI 生成的代码可以很快，但产品是否正确仍然依赖需求和验收设计。
