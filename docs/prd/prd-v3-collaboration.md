# PRD V3 - 工地考勤记账（协同闭环版）

## 0. 文档信息

| 项 | 内容 |
| --- | --- |
| 产品名称 | 工地考勤记账 |
| 文档类型 | PRD |
| 版本 | V3.0 |
| 本期定位 | 从“单向记录”升级为“员工核对 + 管理员处理 + 结果闭环” |


## 1. 版本目标

V1 解决“记录”，V2 解决“效率”，V3 解决“协同与信任”。

工地场景中，员工最容易产生争议的并不是“是否有记录”，而是“记录对不对”。尤其借支明细，如果没有统一入口和核对机制，月底极易出现误解。V3 的目标是建立一个轻量但闭环的“有疑问就提、有问题可改、处理状态可追踪”的机制。

本期核心目标：

1. 员工看到借支后可以发起疑问。
2. 疑问能带着上下文到达管理员。
3. 管理员可以查看对应借支、直接修改或删除。
4. 疑问有状态流转，直到处理完成。
5. 借支记录与疑问处理形成完整闭环，提升员工信任感。

## 2. 升级背景

在 V2 阶段，数据已经可查可导，但还存在新的业务痛点：

1. 员工发现借支有问题时，不知道去哪里反馈。
2. 管理员收到口头质疑后，需要反复翻聊天记录和借支台账。
3. 截图、日期、金额、支付方式等证据散落，定位一笔借支成本高。
4. 处理结果没有状态记录，员工不知道问题是否被看见。

## 3. 用户与价值

| 用户 | 本期价值 |
| --- | --- |
| 员工 | 有正式反馈入口，不必反复私聊管理员 |
| 管理员 | 能带着上下文处理问题，减少来回解释 |
| 团队 | 建立“记录可核对、问题可处理”的信任机制 |

## 4. 产品范围

### 4.1 本期范围

1. 借支记录凭证上传。
2. 员工对借支发起疑问。
3. 员工可选择将疑问通过分享卡片发送给管理员。
4. 管理员首页展示待处理疑问数量。
5. 管理员查看疑问详情、对应借支、员工历史借支。
6. 管理员在线修改或删除问题借支。
7. 管理员标记疑问为已回复或已解决。
8. 预留订阅消息通知能力。

### 4.2 不在本期范围

1. 多轮会话式客服系统。
2. 语音、视频举证。
3. 法务级电子签名或不可篡改审计。
4. 与工资条自动联动申诉。

## 5. 关键业务场景

### 5.1 员工发现借支异常

1. 员工进入“我的借支”。
2. 点击某条借支的“有疑问”。
3. 输入疑问内容。
4. 选择“仅提交”或“提交并分享给管理员”。
5. 系统生成疑问记录。

### 5.2 管理员处理疑问

1. 管理员进入首页，看到“员工疑问 N 待处理”。
2. 打开疑问列表，选择一条疑问。
3. 查看员工、提交时间、疑问内容、对应借支、该员工历史借支。
4. 如确有问题，直接修改金额、日期、支付方式、备注，或删除记录。
5. 将疑问标记为已处理。

### 5.3 分享触达

1. 员工提交疑问后，若担心管理员漏看，可点击分享。
2. 管理员从分享卡片进入，直接打开该疑问详情。
3. 处理后可在系统内留下结果状态。

## 6. 成功指标

1. 员工关于借支的口头投诉量下降 50%。
2. 疑问处理平均时长小于 24 小时。
3. 进入系统后被处理完成的疑问比例大于 90%。
4. 月底因借支数据不一致导致的重复对账次数下降。

## 7. 状态流设计

### 7.1 疑问状态

| 状态 | 含义 |
| --- | --- |
| `pending` | 员工已提交，管理员尚未处理 |
| `replied` | 管理员已回复，但问题未必完结 |
| `resolved` | 管理员已处理完成，问题关闭 |

### 7.2 借支处理流

1. 借支创建
2. 员工查看
3. 员工发起疑问
4. 管理员查看详情
5. 管理员修改/删除/回复
6. 标记处理完成

## 8. 详细需求

### 8.1 借支凭证

| 编号 | 需求 |
| --- | --- |
| FR-901 | 管理员新增借支时可上传最多 3 张图片凭证。 |
| FR-902 | 图片需上传至云存储，并与借支记录关联。 |
| FR-903 | 管理员在借支详情页可预览凭证图片。 |

### 8.2 员工疑问发起

| 编号 | 需求 |
| --- | --- |
| FR-911 | 员工在“我的借支”中可对任意借支记录点击“有疑问”。 |
| FR-912 | 发起疑问时必须填写疑问内容。 |
| FR-913 | 提交后生成一条疑问记录，默认状态为 `pending`。 |
| FR-914 | 员工可选择“仅提交”或“提交并分享”。 |

### 8.3 分享给管理员

| 编号 | 需求 |
| --- | --- |
| FR-921 | 系统生成带 `questionId` 的分享路径。 |
| FR-922 | 分享标题需包含员工姓名、借支金额、借支日期、疑问摘要。 |
| FR-923 | 管理员从分享卡片进入后，应直接打开疑问详情。 |

### 8.4 管理员疑问列表

| 编号 | 需求 |
| --- | --- |
| FR-931 | 首页展示待处理疑问数量。 |
| FR-932 | 管理员可打开疑问列表，按提交时间倒序查看。 |
| FR-933 | 每条疑问至少展示员工姓名、状态、内容摘要、提交时间。 |

### 8.5 疑问详情处理

| 编号 | 需求 |
| --- | --- |
| FR-941 | 管理员可查看员工信息、疑问内容、提交时间、处理状态。 |
| FR-942 | 若疑问关联借支，应展示对应借支的金额、日期、支付方式。 |
| FR-943 | 系统应尽量同时展示该员工其他借支记录，辅助判断。 |
| FR-944 | 管理员可直接修改借支金额、日期、支付方式、备注。 |
| FR-945 | 管理员可删除错误借支记录。 |
| FR-946 | 管理员可将疑问标记为“已处理完成”。 |

### 8.6 消息触达预留

| 编号 | 需求 |
| --- | --- |
| FR-951 | 系统预留订阅消息能力，用于考勤催办与疑问处理通知。 |
| FR-952 | 模板消息应包含员工姓名、月份/疑问内容、时间。 |
| FR-953 | 若员工未绑定微信，不发送通知并提示原因。 |

## 9. 数据设计

### 9.1 新增集合

| 集合 | 核心字段 |
| --- | --- |
| `advance_questions` | `advanceId`、`workerId`、`workerName`、`content`、`status`、`createTime`、`replyContent`、`replyTime`、`resolveTime` |

### 9.2 涉及集合

| 集合 | 用途 |
| --- | --- |
| `advances` | 借支主体记录，支持图片凭证与在线修改 |
| `workers` | 员工身份映射与通知目标 |
| `users` | 管理员权限校验 |
| `advance_questions` | 疑问记录闭环 |

## 10. 权限与安全

1. 只有员工本人可发起自己的借支疑问。
2. 只有管理员可查看全部疑问并修改借支数据。
3. 删除员工时必须级联删除其借支与考勤，避免脏数据。
4. 敏感字段应清理，不在工人资料中长期保存身份证、银行卡等高敏信息。
5. 所有处理行为至少要有状态变更记录。

## 11. 非功能需求

1. 分享卡片进入后应能直接命中疑问详情，减少跳转层级。
2. 借支编辑弹窗需支持移动端快速修改，不依赖复杂表单。
3. 疑问详情页打开时间应控制在 2 秒内。
4. 云存储图片预览需稳定可用。

## 12. 开放问题

1. 管理员是否必须填写回复内容，还是允许直接标记已解决。
2. 是否需要给员工展示“我的疑问”列表和处理状态。
3. 借支修改后是否需要保留版本历史，满足事后追溯。

## 13. 里程碑

| 阶段 | 交付内容 |
| --- | --- |
| M1 | 借支凭证上传与详情预览 |
| M2 | 员工疑问提交、疑问数据模型 |
| M3 | 管理员疑问列表与详情处理 |
| M4 | 分享直达与订阅消息预留接入 |

## 14. 风险与应对

1. 旧借支数据字段不统一，疑问关联时可能需要兼容 `worker_id/workerId`、`worker_name/workerName`。
2. 管理员直接修改借支会带来“谁改过”的审计需求，后续可能需要增加操作日志。
3. 图片上传过多会增加云存储成本，需要限制数量与大小。
4. 分享触达依赖管理员及时查看消息，仍建议后续结合订阅通知。

## 15. 验收标准

1. 员工可针对任意借支成功提交疑问。
2. 管理员首页可看到待处理疑问数。
3. 管理员可在疑问详情中修改或删除对应借支。
4. 疑问状态能从 `pending` 变更为 `resolved`。
5. 分享卡片能直达对应疑问详情页。
