## 1. Release 定位

这是一个可在微信开发者工具中导入、配置并部署的轻量级工地管理小程序。项目的核心价值不是替代 ERP 或工资系统，而是把施工团队中分散在纸张、微信群和口头沟通里的基础台账统一到一个移动入口中。

当前版本聚焦三条业务链：

- **记录链**：员工、项目、借支、考勤数据可建立和查询。
- **提效链**：管理员可按月查看考勤进度、筛选数据并导出 Excel。
- **协同链**：员工可对借支发起疑问，管理员可查看上下文、修改记录并关闭问题。

> 当前仓库以微信开发者工具为主要运行入口。README 描述的是仓库中已经存在的实现与交付约束，不把未来规划写成已完成能力。

## 2. 适用对象

### 使用者

- **管理员**：包工头、班组长、现场管理者。
- **员工**：参与项目施工并需要填报考勤、核对借支的工人。

### 开发者

- 需要学习微信小程序原生开发和 CloudBase 云函数的开发者。
- 需要把 PRD 转换为结构化任务、交给 AI Coding Agent 执行的团队。
- 需要一个小型真实业务项目作为作品集或面试讲解材料的开发者。

## 3. 已实现能力

### 管理员端

- 管理员邀请码登录和角色识别。
- 员工档案新增、编辑、删除、绑定状态查看。
- 项目新增、编辑、完工状态维护。
- 借支新增、编辑、删除、支付方式和备注记录。
- 借支凭证上传与员工借支疑问处理。
- 按月份查看考勤提交进度、已提交和未提交人员。
- 查看考勤明细和月度公示报表。
- 导出员工、考勤、借支 Excel 文件。
- 从疑问入口查看员工、借支和历史记录，并标记处理状态。

### 员工端

- 选择并绑定员工身份。
- 查看个人资料、历史考勤和借支记录。
- 填报上月及更早月份的项目考勤。
- 对借支记录发起疑问。
- 通过分享路径把疑问上下文带给管理员。
- 编辑个人资料。

### 交付设计资产

- `docs/prd/`：V1 基础数字化、V2 管理提效、V3 协同闭环 PRD。
- `DESIGN.md`：移动端视觉与交互约束。
- `docs/ui/`：高保真 UI 参考板。
- `DOC_INDEX.md`：CloudBase 数据库索引创建说明。

## 6. 数据模型与兼容约束

### 核心集合

| 集合 | 用途 | 关键字段 |
| --- | --- | --- |
| `users` | 用户和角色 | `_openid`、`role`、`name`、`phone` |
| `workers` | 员工档案 | `name`、`phone`、`team`、`status`、`openid` |
| `projects` | 项目档案 | `name`、`status`、`createTime`、`finishTime` |
| `attendance` | 月度考勤 | `worker_id`、`month`、`entries[]`、`submitted_at` |
| `advances` | 借支记录 | `worker_id`、`worker_name`、`amount`、`date`、`method`、`remark` |
| `advance_questions` | 借支疑问 | `advanceId`、`workerId`、`content`、`status`、处理时间 |

### 必须保持的业务规则

1. 一个微信 OpenID 只能绑定一个员工，一个员工只能绑定一个微信身份。
2. 未绑定员工不能进入员工数据链路。
3. 管理员可查看和维护全量数据，员工只能读取和提交自己的数据。
4. 员工考勤按“员工 + 月份”保存，`entries[]` 保存多个项目的出勤明细。
5. 员工端只展示可用项目，已完工项目不得进入新的考勤填报选择器。
6. 同一员工同一月份重复提交时，以最新提交结果覆盖旧记录。
7. 借支历史数据可能同时存在 `worker_id/workerId`、`worker_name/workerName`，查询和迁移不得无意丢失旧数据。
8. 删除员工必须级联处理相关借支和考勤，避免产生孤儿记录。
9. 权限校验必须在云函数完成，前端隐藏按钮不能作为安全边界。

索引创建方式见 [DOC_INDEX.md](./DOC_INDEX.md)。

## 7. 本地运行与部署

### 7.1 前置条件

1. 安装微信开发者工具。
2. 准备已认证或可用的微信小程序 AppID。
3. 开通微信云开发，并准备一个云环境。
4. 确认当前账号拥有云数据库、云存储、云函数部署权限。

### 7.2 导入项目

1. 克隆仓库：

   ```bash
   git clone https://github.com/zhougzzy/project.git
   ```

2. 使用微信开发者工具导入仓库根目录。
3. 检查 `project.config.json` 中的 `appid`、`miniprogramRoot`、`cloudfunctionRoot`。
4. 在 `miniprogram/app.js` 中确认云环境 ID 与目标环境一致。
5. 创建数据库集合并按 [DOC_INDEX.md](./DOC_INDEX.md) 创建索引。
6. 为每个云函数安装依赖并上传部署。带 Excel 导出的函数需要安装 `node-xlsx`。
7. 在开发者工具中编译，完成管理员登录、员工绑定、考勤提交、借支和导出链路验证。

### 7.3 云函数依赖

每个云函数是独立部署单元，不要只在仓库根目录安装依赖。执行方式示例：

```bash
cd cloudfunctions/login
npm install
```

需要 `node-xlsx` 的函数包括：

- `exportWorkers`
- `exportAttendance`
- `exportAdvance`

当前仓库没有统一根目录 `package.json`，因此构建、上传、预览和云函数部署以微信开发者工具为准。

## 8. AI Coding 开发契约

本节是交给 Coding Agent 的最小工作协议。任何 AI Agent 在改代码前都应先阅读本节、对应 PRD、`DESIGN.md` 和相关页面/云函数。

### 8.1 需求输入格式

每个需求必须说明：

- **目标**：要解决的用户问题和业务结果。
- **角色**：管理员、员工，或公共流程。
- **范围**：涉及页面、云函数、集合、索引和文档。
- **不做什么**：明确非目标，避免 Agent 扩大范围。
- **数据契约**：输入字段、输出字段、状态值、兼容旧字段。
- **安全边界**：谁可以读、写、修改、删除。
- **验收标准**：可以被人工或自动检查的 Given/When/Then 条件。

推荐需求卡模板：

```md
# [TASK-XXX] 任务标题

## 目标
一句话说明用户价值和交付结果。

## 角色与范围
- 角色：管理员 / 员工 / 公共
- 修改范围：页面、云函数、数据集合、文档
- 非目标：本任务明确不处理的内容

## 约束
- 必须遵守的业务规则
- 权限和数据安全要求
- 兼容字段和性能限制
- UI 必须遵守 DESIGN.md

## 验收标准
- Given ... When ... Then ...
- Given ... When ... Then ...

## 交付物
- [ ] 代码
- [ ] 数据库或索引变更说明
- [ ] 测试或手工验证记录
- [ ] README / PRD 更新（如需要）
```

### 8.2 Agent 执行顺序

1. **理解**：读取任务卡、相关 PRD、页面、云函数和数据模型。
2. **勘察**：列出将修改的文件、现有调用链、风险和未知项。
3. **设计**：先给出最小实现方案和数据契约，再开始修改。
4. **实现**：只修改任务范围内文件，沿用现有原生小程序和 CloudBase 模式。
5. **验证**：运行可用的静态检查，逐条执行验收标准，检查角色权限和空状态。
6. **交付**：说明修改文件、数据变更、验证结果、未解决风险和后续任务。

### 8.3 Agent 输出格式

```md
## 实现摘要

## 修改文件

## 数据与权限变更

## 验收结果
- [x] AC-1 ...
- [ ] AC-2 ...（原因）

## 风险与后续
```

### 8.4 编码约束

- 保持微信小程序原生技术栈，不无故引入框架或构建系统。
- 优先复用 `miniprogram/utils/cloudCall.js`，避免页面重复实现重试和错误提示。
- 云函数必须使用 `cloud.DYNAMIC_CURRENT_ENV`，不得把环境 ID 硬编码到服务端逻辑。
- 所有写操作必须做参数校验、权限校验和失败反馈。
- 所有列表必须处理加载中、空数据、异常、分页或数量上限。
- 所有金额、日期、月份和状态字段必须保持已有格式，变更前先检查历史数据。
- 前端展示逻辑可以改善，但不能替代后端授权。
- 不提交密钥、AppSecret、用户隐私数据、生产导出文件或本地临时文件。
- 保持变更小而完整；不要在功能任务中顺手重构无关模块。

## 9. 任务卡路线图

任务卡按依赖顺序组织。每张卡都可以由一个 Coding Agent 独立领取，完成后再进入下一张。

### 基础与工程质量

#### TASK-001：建立可重复的项目检查入口

- **目标**：让提交前至少能够执行统一的 JSON、JavaScript 和结构检查。
- **范围**：新增根目录开发检查说明或轻量脚本，不改变运行时行为。
- **约束**：适配微信小程序目录结构；不能假设存在统一前端构建工具。
- **验收**：
  - 能检查 `project.config.json`、`miniprogram/app.json` 和所有 `package.json` 的合法性。
  - 能扫描云函数入口文件是否存在。
  - 检查失败时返回非零状态并指出文件。

#### TASK-002：统一云函数调用与错误模型

- **目标**：减少页面直接调用 `wx.cloud.callFunction` 造成的错误处理差异。
- **范围**：`miniprogram/utils/cloudCall.js` 和逐步迁移页面。
- **约束**：保留现有调用方式兼容性；重试只用于可安全重试的网络失败，不重复提交业务写操作。
- **验收**：
  - 成功、业务失败、网络失败、超时均有稳定的用户反馈。
  - 提交考勤、创建借支等写操作不会因重试造成重复数据。
  - 至少一个读取链路和一个写入链路完成迁移验证。

### 身份与权限

#### TASK-003：收紧管理员与员工数据权限

- **目标**：保证员工只能读取自己的数据，管理员权限在服务端生效。
- **范围**：`login`、绑定函数、员工/借支/考勤相关函数和数据库权限。
- **约束**：不能仅依赖前端角色字段或隐藏按钮。
- **验收**：
  - 未绑定用户调用员工数据接口返回明确拒绝。
  - 员工无法通过篡改 `workerId` 读取他人借支或考勤。
  - 非管理员无法新增、编辑、删除全员数据。
  - 管理员操作仍能正常完成。

#### TASK-004：完善绑定幂等性与解绑纠错流程

- **目标**：降低误绑定、重复绑定和并发点击带来的脏数据风险。
- **范围**：`bindWorker`、`bindWorkerWechat`、绑定页面。
- **约束**：一个 OpenID 只能绑定一个员工，一个员工只能绑定一个 OpenID。
- **验收**：
  - 重复提交同一绑定请求不会生成重复关系。
  - 已绑定员工和已绑定微信均有明确提示。
  - 并发或重复点击后最终数据只有一个有效绑定关系。

### 员工、项目与借支

#### TASK-005：统一借支字段和兼容查询层

- **目标**：消除 `worker_id/workerId`、`worker_name/workerName` 并存造成的查询分叉。
- **范围**：借支云函数、员工借支页面、历史数据迁移说明。
- **约束**：迁移前必须保留旧字段读取能力；金额不能静默改变。
- **验收**：
  - 新写入记录使用统一字段。
  - 历史两种字段命名都能被员工和管理员查询到。
  - 导出结果不重复、不漏记，并给出迁移或兼容说明。

#### TASK-006：项目生命周期与填报项目一致性

- **目标**：已完工项目不再出现在新的员工考勤选择器中。
- **范围**：项目列表、`getProjects`、员工考勤页面。
- **验收**：
  - 管理员可编辑名称并标记完工。
  - 完工项目保留历史记录，但从新填报列表移除。
  - 无可用项目时有明确空状态和可恢复入口。

#### TASK-007：借支凭证上传与大小限制

- **目标**：为借支记录保留可核对的图片凭证。
- **范围**：借支新增页面、云存储、借支详情和数据字段。
- **约束**：限制图片数量和单张大小，失败时不能生成无凭证假记录。
- **验收**：
  - 最多上传 3 张凭证并能预览。
  - 上传失败、删除失败和网络中断均有可理解提示。
  - 员工只能查看自己有权限查看的借支内容。

### 月度考勤与报表

#### TASK-008：考勤提交校验与幂等覆盖

- **目标**：保证月度考勤数据符合业务规则且重复提交可控。
- **范围**：`submitAttendance`、员工考勤页、`attendance` 集合。
- **验收**：
  - 只能提交上月及更早月份。
  - 每个项目天数不小于 0，不能超过当月自然日。
  - 项目天数总和不能超过当月自然日。
  - 同一员工同一月份重复提交后只有一条有效记录，且状态显示已提交。

#### TASK-009：月度看板统计口径统一

- **目标**：让应填报、已填报、未填报、完成率在所有页面使用同一口径。
- **范围**：`getAttendanceSummary`、首页、考勤列表、公示报表。
- **验收**：
  - 月份切换后统计值同步更新。
  - 已填报人数按员工去重。
  - 无待填报时展示“全部完成”空状态。
  - 首页、明细和导出结果的员工范围一致。

#### TASK-010：导出任务可靠性与数据脱敏

- **目标**：让员工、考勤、借支导出可复核、可控量、可追踪。
- **范围**：`exportWorkers`、`exportAttendance`、`exportAdvance`。
- **约束**：导出只允许管理员执行；限制最大行数；文件名包含范围和生成时间；手机号等字段按发布要求脱敏。
- **验收**：
  - 三类导出均能打开并包含列头、数据和范围信息。
  - 超出上限时返回明确提示，不生成不完整的“成功”文件。
  - 非管理员调用被拒绝。

### 协同闭环

#### TASK-011：借支疑问状态机

- **目标**：把员工反馈、管理员处理和结果状态连成闭环。
- **范围**：`advance_questions`、我的借支、管理员首页和处理弹层。
- **状态**：`pending -> replied -> resolved`，必要时允许管理员直接 `pending -> resolved`。
- **验收**：
  - 员工只能对自己的借支发起疑问。
  - 疑问必须有内容，默认状态为 `pending`。
  - 管理员能看到待处理数量、对应借支和员工历史记录。
  - 管理员处理后状态可变更为 `resolved`，数量同步减少。

#### TASK-012：分享路径直达疑问详情

- **目标**：降低管理员从分享卡片进入后的跳转成本。
- **范围**：分享配置、首页参数解析、疑问详情加载。
- **验收**：
  - 分享路径包含有效 `questionId`。
  - 管理员进入后能直接定位对应疑问。
  - 无效或已处理疑问有明确状态提示，不白屏、不误操作。

## 11. 已知限制

- 当前没有根目录统一构建脚本和自动化测试套件。
- 部分页面仍直接调用 `wx.cloud.callFunction`，调用封装尚未完全统一。
- CloudBase 集合、索引、权限和环境配置需要在微信开发者工具中完成。
- 大规模跨月份导出需要进一步评估分页、异步任务和文件大小限制。
- 借支历史字段存在兼容命名，完全统一仍需要数据迁移任务。
- 订阅消息函数已预留，实际通知模板和用户授权仍需按发布环境配置。
